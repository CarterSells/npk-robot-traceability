## Use the workflow

Open the development workspace, or the configured private beta, and choose **Compare → Target run**. Under **Investigate this run**, choose an earlier successful baseline for the same robot. A suggestion is offered only when recorded core procedure/object/conditions and custom comparison checks produce no warnings. It explains the choice and requires a click; it never automatically selects the latest success. Missing physical observations remain unverified. You may select a less comparable earlier success manually; limitations remain visible.

Expand grouped differences to inspect values, missing fields, units and both snapshots' evidence references, methods, authors and observed/recorded times. References are displayed as text and never fetched. Reported availability is not verified access. Manual hardware over 24 hours old is highlighted under the existing prototype policy.

Enter an author, note and state, then **Append investigation entry**. States are investigating, hypothesis, confirmed-by-engineer and unresolved. Confirmation requires an evidence note or an existing later retest of the same robot, observed by the entry's recorded time. A failed or differently configured retest does not automatically prove a resolution; the engineer is responsible for the conclusion. Reports include retest outcomes and comparison warnings. State changes may reopen an investigation; every appended revision remains in history.

Use **Investigation history** to reopen a saved investigation for the selected target. Its original target/baseline remain fixed. Start a new investigation to choose another pair. Snapshot corrections do not rebind its historical runs. Author names in imports/local entries are reported provenance; beta submission audit separately records the authenticated actor.

Local changes remain in tab memory until **Export JSON**. Import that workspace file to restore all notes and exact record references. In beta, **Save to organization** persists the draft; reload then reopen the target/history. Viewers may read and export but cannot append. Collector captures cannot add investigation conclusions.

**Export investigation report** downloads a version-1 `unify-investigation-report` JSON artifact: current assessment, full revision history, grouped comparison, limitations, original snapshots/provenance and any referenced retests with their exact snapshots. It reflects the current draft, including unsaved entries, and preserves the synthetic label. This report is not a full workspace backup or a client publication. Import the workspace export, not the report, to resume editing. Keep private files outside the repository.

## Contract and deployment

Workspace version 2 supports an optional `investigations` array of at most 1,000 revision entries within the existing 2 MiB limit. Versions 1 and 2 without this field remain readable. Earlier application releases reject the new field; do not downgrade a workspace by stripping it. Each entry contains UUID `id`, contiguous `revision`, fixed `runId`/`baselineId`, `state`, reported `author`, UTC `recordedAt`, required `note`, and `evidenceNote`/`retestId` strings (empty when absent). Revisions are ordered per investigation. Imports reject unknown fields, broken references, incomplete history and invalid confirmations. Local JSON is editable, not cryptographically tamper-proof.

For a new beta environment, first inspect the existing schema and migration state as described in [B1 activation](backend-activation.md). Apply `supabase/migrations/20261016040114_stage7_investigations.sql` once after the original private-beta migration. The original migration is unchanged. The selected hosted project already has this schema; its applied version identifiers are mapped in [hosted activation](hosted-supabase.md). Do not replay repository migrations there. No live migration was executed during the October 16 implementation; hosted activation followed on October 18.

The new migration extends the existing `investigations` table with an immutable `investigation_revisions` relation. The existing `beta_command` transaction writes records and its audit event; an audit trigger then validates/persists investigation revisions and projects the latest state into `investigations`. Failures roll back the entire save. Revision rows use organization-qualified foreign keys, RLS, read-only authenticated grants and the exact audit `submitted_version`. The workspace bundle remains the current import/export representation. Existing Stage 6 investigation rows without revision history are not silently overwritten: inspect and explicitly migrate any such records before reuse.

The API checks that investigation storage is readable before saving an investigation-bearing bundle, retaining the draft with an actionable error if unavailable. This check is not a complete migration attestation; administrator inspection must verify the trigger, grants and constraints too. Schema/domain validation remains in the trusted API, with SQL checks for immutable history, authorization, relationships and confirmation evidence. Administrators/service credentials remain privileged, as in Stage 6.

Rollback: disable beta writes and preserve a complete database backup and workspace exports. Do not drop history or remove the migration to run an older application. Restore only to an isolated environment with compatible application/schema versions. Test reload, exports, exact snapshots, audit actors, tenant/viewer denial and collector restrictions for each deployed environment before customer use.
