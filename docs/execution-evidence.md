# B6 execution evidence

Governed by [build.md](../build.md) and [B6](backend-master-prompts.md). Implements deterministic projection, append-only storage, human and machine ingestion, complete history exports and an internal timeline. The existing B5 `run.recorded` contract remains compatible. See progress for exact activation and verification evidence; these capabilities do not establish customer validation or physical execution.

## Evidence contract

A job identifies the requested work. Each attempt has a separate UUID and optional `retry_of` reference to another attempt in that same job. Recording either does not execute anything. Attempts reference an existing project/robot association and exact immutable snapshot revision; a foreign snapshot or revision is rejected. Existing completed test records remain authoritative and are not rewritten or silently converted into lifecycle records.

`lib/beta/lifecycle.ts` defines the strict input contract. Procedure, procedure version, task, environment and component description are explicitly known, unknown or not-applicable. Reality (`real`, `simulation`, `synthetic`) is separate from collection method (`manual`, `collector`); a manual report can describe any of these realities. The human writer accepts manual reports with the authenticated user's UUID as source identity. The machine writer requires collector method and the scoped machine UUID. Synthetic workspace boundaries still apply.

Each event has a UUID, stable source identity, per-attempt durable integer source sequence, UTC observed timestamp, kind, approved payload, optional prior event UUID and correction reason. The database adds receipt time and authenticated author. Event kinds are state, acknowledged, step, measurement, label and component. No raw recordings, arbitrary binary content or unrestricted payload properties are accepted. Free-text evidence references still require human metadata review.

Supported states are requested, queued, running, succeeded, failed, cancelled, timed-out and unknown. Missing intermediate reports may be skipped; acknowledgement alone changes no state. Unknown may be resolved by evidence. Requested can advance to queued/running/terminal, queued to running/terminal, and running to terminal. Terminal repeats are permitted. Conflicting terminal results produce unknown with warnings until corrected. Timed-out is uncertainty, not observed completion: a later success/failure/cancellation may resolve it. No wall clock automatically fabricates timeout or failure.

Source sequence, not delivery order or device wall clock, orders evidence from the attempt's single source. Retries with identical event content return the original receipt. A different event at the same sequence or changed content at the same UUID conflicts. Out-of-order delivery remains permissible. The caller must retain event IDs and sequences across restarts. For machines, sequence allocation spans the identity's capture and lifecycle events, not just one attempt. The B5 queue now validates, persists, retries and reconciles both event types; private-path, capacity and power-loss limitations remain unchanged.

Corrections append a replacement for an active prior event of the same kind and evidence identity, with a reason. Projection retains the original position in the execution sequence. Raw events and authors remain visible. Unresolved or invalid correction references produce warnings and unknown outcome rather than silently discarding uncertainty. A received-time cutoff reconstructs what was known at that time. Competing measurements become unknown; incompatible units are flagged, never silently converted. Competing quality labels are withheld pending correction.

Measurements require name, evidence state, unit, numeric value or null and missing reason. `duration` and `downtime` use seconds; unknown is never zero. Workload and intervention counts may use explicitly named unit-qualified metrics. Labels include a name, value and evidence reference. Component installation/removal/maintenance/service events include component identity, evidence, and hours/cycles or null. They do not alter historical snapshots or prove a physical action occurred.

## API and storage

With `BETA_LIFECYCLE_ENABLED=true` after migration and verification, `/api/org/<org>/executions` accepts authenticated human requests:

- POST `{action:"create", project_id, attempt}` using the `Attempt` contract.
- POST `{action:"append", attempt_id, event}` using `LifecycleEvent`.
- GET lists 25 attempts in stable UUID order; `after` continues the current scan. Concurrent additions may require refreshing from the beginning.
- GET `?attempt=<uuid>` returns context and projected timeline; optional `known_at=<UTC milliseconds timestamp>` limits evidence by receipt time.

The server verifies membership and writer roles; the service-only database function repeats capability checks and restricts the writer to the attempt's source identity. Viewers may read internal evidence but cannot append. External client grants expose none of these tables or endpoints. New public tables have RLS and immutable update triggers; anonymous/authenticated roles cannot execute the writer RPC. Tenant-qualified foreign keys enforce project, robot, snapshot and retry relationships.

Machines submit `execution.recorded` to the existing `/api/v1/events` endpoint. The envelope's `run_id` is the attempt UUID, and `payload` contains the immutable `attempt` plus `evidence` (`kind`, `payload`, `correction_of`, `reason`). Each event repeats the same attempt context so delivery order does not control creation. The snapshot must already exist; retry attempts require their original attempt to exist. Scope comes from the credential. Creation and event/receipt persistence commit atomically. Existing GET receipt reconciliation, rotation, expiry, revocation and shared request limits apply. See the [envelope](api/event-v1.schema.json), [execution payload](api/execution-v1.schema.json), [OpenAPI](api/openapi-v1.json) and [queue commands](machine-ingestion.md). Execution receipt `version=1` identifies its receipt format, not workspace or event ordering.

The CLI-generated migration is `20261025000520_b6_lifecycle.sql`; once applied, do not edit it. Events are limited to 1,000 per attempt and 16 KiB per normalized execution envelope; overflow preserves stored history and rejects further writes. These are explicit staging bounds, not demonstrated target-load capacity. Complete history exports become version 2 when lifecycle is active: snapshot history and lifecycle collections share a manifest captured under the organization lock, with per-collection cutoffs, reauthorization on every page and a final completion marker. They include jobs, attempts and raw events with author/receipt provenance. Private credential hashes and receipts remain database-backup metadata. The bounded local importer does not accept this archive. Rollback disables new lifecycle writes and retains tables; archive access should remain available operationally for accepted evidence rather than discarding it.

The internal timeline shows reality/method, snapshot revision, state, warnings, measurements, labels, raw event provenance and corrections. It is explicitly refreshed, not described as live. Predictions are unavailable. See [progress](build-progress.md) for actual checks and remaining work.
